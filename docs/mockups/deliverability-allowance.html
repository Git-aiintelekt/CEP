Deliverability tests — one Mailgun account for the platform, tests by plan, top-ups by workspace. Mockup, not the product. The platform team enters one Mailgun Inspect account in the back-office; every workspace runs its inbox previews through it, up to its plan's number each month (Starter 10, Growth 50, Enterprise unlimited). For a busy month the platform team adds tests to one workspace (“NWA: +70 for October”); added tests end with the month. A workspace may still connect its own Mailgun account instead. Parts 1 and 2 are the back-office (its own palette); part 3 is what a workspace sees in the app.

What gets built, in words

The platform's account

  • The account table gains the platform's own row (tenant empty), as the mail server already does: back-office → Configuration → Mailgun Inspect (region, username, encrypted key, default clients, Check Connection), platform staff only.
  • A workspace's test uses its own account when it has one, otherwise the platform's. The workspace keeps its own choice of clients. Each test sent through the shared account carries the workspace's code in its Mailgun reference, so the platform team can tell them apart in Mailgun too.

The number of tests

  • This month's allowance = the plan's number + the workspace's additions for this month (unlimited stays unlimited). Additions end with the month. Table tenant_quota_grant (workspace, metric, month, tests, note, who, when, removed); every change in the workspace's audit trail.
  • The limit, Plan and Usage, the template tab and the message at the limit all read that one number.

One decision left

A workspace on its own Mailgun account pays Mailgun itself. Should its tests still count against the plan? Recommended: no — the plan's number protects the platform's account; a workspace using its own is limited only by its Mailgun subscription (its count still shows on Plan and Usage).

Recommendation
