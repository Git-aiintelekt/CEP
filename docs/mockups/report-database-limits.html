Mockup, not the product. Static HTML on the app's colour and shape values. Settings → Report Databases, the Connect a Database / Edit dialog and the database cards. Sample databases.

Each Report Database gets its own time limit (how long one report may read it) and reports at once (how many may read it at the same time). Workspace administrators set them in the app; no restart is needed, the next report uses them. The back-office keeps the workspace's default. Both options change the same two values; they differ in how they are asked for.

What gets built, in words

  • Two values per connection on report_connection: query_timeout_s (5–110, empty = the workspace's default, 15 unless the back-office raised it) and max_concurrent (1–4, empty = 4). A patch adds them; nothing else changes for existing connections.
  • The dialog (Connect a Database / Edit, under Settings → Report Databases and from New Report) gets the Limits section of the chosen option; workspace administrators set it, as they set the rest of the connection. Saved like the other fields; the next report uses it, nothing restarts.
  • The runner uses the connection's time limit for every report, preview, export and query on that database, and a slot per connection (as it keeps one per workspace today), so a second report waits rather than adds load. Scheduled reports follow the same limits.
  • Reading the catalogue (the table list, columns, Test Connection) takes at least 60 seconds, or the time limit when it is longer.
  • The 110-second ceiling stays: the web server stops a request after 120. The back-office Query Limits keep the workspace's default and are refused above 110.
  • The messages name the database and its limit, as shown above.
  • Help: the Report Databases chapter gets the step "Set how long reports may read a database"; the Platform Guide says the per-connection values win over the workspace default.
  • Tests: the fields and their ranges, saving them, the runner using the connection's limit and slot, a second report waiting.
Recommendation: Option B. The people who connect a database know what kind it is (a live production database, a reporting copy) far better than what a good number of seconds is. The presets put that knowledge to use, Live Production Database makes the careful choice the obvious one for a database like CG-Prod, and Custom keeps the exact values for anyone who wants them.
